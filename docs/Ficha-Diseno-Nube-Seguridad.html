🔒 Bloque 2: Las 3 Reglas de Seguridad
1. En el teléfono del usuario (Protección contra robo de datos):
No se guardan contraseñas en el dispositivo. El token de sesión JWT se almacena cifrado con flutter_secure_storage mediante hardware seguro (Android Keystore / iOS Keychain). En caso de cierre o caducidad, el almacenamiento seguro se purga automáticamente.
2. En el viaje de los datos (Cifrado en tránsito):
Toda la comunicación móvil-nube viaja exclusivamente bajo HTTPS/TLS 1.3 hacia el host seguro (tandea-back-end-production.up.railway.app). Cada petición a endpoints protegidos incluye la cabecera estándar Authorization: Bearer <token_jwt>.
3. En la base de datos (Aislamiento entre usuarios):
Control de acceso en el backend mediante JwtAuthGuard y reglas de dominio: el servidor valida el idUser del token y restringe lectura o mutación; únicamente el organizador (idAdmin) o el titular asignado a ese turno pueden consultar o confirmar sus registros.
🛡️ Bloque 3: Protección del Código (Buenas Prácticas)
¿Cómo ocultarán las credenciales (API Keys) para que no se suban por error a repositorios públicos (GitHub)?
  • Exclusión obligatoria en Git: Los archivos locales .env que contienen la DATABASE_URL, secretos JWT y credenciales de correo/nube están agregados a los .gitignore de Frontend y Backend.
  • Plantilla pública desacoplada: Únicamente se versiona .env.example como contrato de referencia con valores vacíos o ficticios.
  • Inyección segura en la Nube: En Railway las llaves se inyectan como variables de entorno privadas encriptadas en el panel. En Flutter se inyectan en tiempo de compilación con --dart-define.
